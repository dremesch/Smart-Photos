# Engineering Review of Specification v1.0 — Findings and Disposition

**Outcome:** v1.0 approved with required changes. Changes promoted into [Technical Specification v1.1](../spec/technical-specification-v1.1.md), which is the implementation authority. v1.0 is retained as the historical baseline.

## 1. Mandatory fixes

| # | Finding | Disposition | Where in v1.1 |
|---|---|---|---|
| 1 | Reading metadata or hashing during inventory hydrates OneDrive online-only placeholders | Accepted — two-pass inventory; cloud state read from directory attributes before any open | §5.2–5.4 |
| 2 | Applying EXIF orientation to HEIC double-rotates images already transformed by `irot`/`imir` | Accepted — single format-aware decoding contract | §6 |
| 3 | Deterministic shortlisting picks group representatives on technical quality alone, so the best expression in a burst may never be evaluated | Accepted, redesigned — lightweight local models on all eligible photos; expensive analysis only for selected groups | §7–9 |
| 4 | Example crop `{w: 0.96, h: 0.80}` on a 4:3 source is 1.6:1, not 3:2; crop search has only one free axis | Accepted — pixel-aspect invariant, oriented dimensions stored, 1-D search | §12 |
| 5 | Native decoder crashes cannot be caught in-process and would terminate the batch | Accepted — restartable decoder subprocesses | §6.4 |

## 2. Other adopted changes

- **Data model:** content-based identity; append-only `DecisionEvent`; `ProtectedRegion`, `LivePhotoPair`, `DeviceClockOffset`, `ProcessingItem`, `ExportItem`; crop invalidation on source/orientation change (§14, §12.8).
- **Metadata:** Apple `BurstUUID` and `ContentIdentifier`; per-device burst grouping and clock offsets; event day = local capture date; provenance-aware ranking (§5.5–5.7, §8).
- **Security and privacy:** `%LOCALAPPDATA%` storage; OneDrive sync-root and Known Folder Move detection; layered network enforcement including optional firewall rule; no face embeddings or clustering (§5.4, §16).
- **Models:** license-gated selection; known exclusions (InsightFace pretrained weights, Ultralytics AGPL) (§4.3).
- **Export:** P3/`nclx` → sRGB via LittleCMS with embedded ICC; SDR base image used for HDR photos; resolution warning; lab auto-crop reminder (§13).
- **Evaluation:** labels created before AI exposure; train/test split; recall alongside precision; crop results with sample counts and confidence intervals (§18–19).
- **Sequencing:** usable review grid in M1; cropping as a parallel workstream (§20).

## 3. Qualified recommendations

| Review recommendation | Qualification adopted |
|---|---|
| Facility-location selection "has the standard (1−1/e) guarantee" | That bound applies to monotone submodular objectives under a cardinality constraint. Redundancy penalties can break monotonicity and partition/quota constraints change the bound. v1.1 states the objective precisely and claims no guarantee unless its conditions are shown to hold (§10.2). |
| Use DirectML as the first GPU path | DirectML is in maintenance mode; Microsoft recommends Windows ML for new Windows deployments. v1.1 benchmarks CPU first, then evaluates Windows ML and DirectML against Python integration constraints (§4.2, §15.5). |
| Per-photo inference timings ("tens of milliseconds") | Treated as hypotheses until M0/M2 benchmarks; decode and inference are measured separately (§7.2). |

## 4. Clarifications made while drafting v1.1

- **HDR handling** is "use the SDR base image, ignore the gain map," not a tone-mapping step (§13.3).
- **Hydration testing** requires a real OneDrive-synced Windows machine; hosted CI covers the attribute logic through a mocked layer only (§18.3).
- **Regrouping between milestones** (pHash/time in M1, embeddings in M2) is safe because decisions are keyed to photos, not groups (§20).
- **Acceptance target values** are set at the end of M0 once the hardware and manual baseline are known (§19).
