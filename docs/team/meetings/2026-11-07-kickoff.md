## 1. Summary

The team accepted the Architect's sprint 1 focus (WP-0 discovery, WP-C contracts, fixtures, CI hardening) and tightened it in three important ways:

1. **Measure before we show.** The owner must not see any POC rankings or crops until the manual baseline and the evaluation labels are done. The baseline comes first, because labelling also familiarises the owner with the photos.
2. **Nothing personal leaves the owner's PC.** All work on Japan 2024 runs headless on the owner's machine under a signed data-handling checklist. Only aggregate numbers come back to the team.
3. **No test seams in product code.** The POC's environment-variable crash trigger is not carried forward. Faults are injected through the `DecoderPort` with a test adapter.

**The M1 pilot is booked for week 6**, with a week-4 dry run on synthetic data. If WP-C slips, the pilot slips; M1 scope is not cut to hold the date.

## 2. Discussion highlights

**PM (opening):** Success for the first real use is the M1 exit criterion only: the owner curates a 300–500 photo batch faster than with Windows Photos, with zero source files changed. No performance promises before M0 sets targets. Face identity stays out, and would be declined as a change request. Pushed for the manual baseline and evaluation labels to happen before the owner sees any AI output.

**Tech Lead:** Turned the work packages into a 12-item sprint 1 backlog. Estimated the earliest owner-testable grid at week 4, realistic at week 6. Named two risks: contract churn after WP-C, and a review bottleneck. Proposed one-week sprints, a Friday written status, a `needs:owner` label, and a cap of two open PRs per role.

**Data Scientist:** About 300 labelled items are needed before model variants can be told apart (a 95% interval is about ±3 points at n=300, ±5 at n=100). Proposed three owner sessions: critical moments, about 600 same/different pairs, and about 150 best-of-group decisions with a repeat set for self-consistency. Shortlisted YuNet, BlazeFace and SCRFD for faces, Face Mesh for eyes, YOLOX/NanoDet/RT-DETR for pets, and SigLIP vs DINOv2 for embeddings. Defined "replaces Haar" as fewer false faces, better recall (including small faces and pets), and fewer false crop conflicts, all measured against Haar on the owner's labels.

**Systems Engineer:** The POC's pool can't kill hung workers, keys its cache on SHA-256 only, and has no memory budget. Will build managed workers with deadlines, kill and respawn, two-strikes quarantine, batched writes, and a reserved interactive worker. Proposed the `ItemResult`, `CacheKey` and `DecoderPort` contracts, plus a headless benchmark script for the owner's PC.

**Quality Engineer:** Synthetic HEICs today lack real `irot`/`imir` and `nclx`, which risks false confidence. Will build a seeded fixture builder with a manifest of expected outcomes, and integrity, privacy and canary-token suites run against the POC now and against ports later. Hosted CI cannot prove non-hydration, so the owner-PC run must be logged.

**UX Engineer:** Proposed the baseline protocol: matched ~400-photo batches, the same task in both tools, timing rules, and Windows Photos on a local copy. Critiqued the POC UI (synchronous reloads, UI writing to SQLite, blocking actions). Defined the M1 grid scope and the UI–service contract. Argued against reusing the review grid for labelling, because practice in our UI would bias the speed test.

**Security & Privacy Engineer:** The POC's socket guard is a tripwire, not a control. Paths leak through error strings and the integrity output. `selection.csv` carries capture times and source hashes into the folder most likely handed to a print lab. Wrote safeguards for the owner-PC run. Gave provisional licence calls: YuNet, SigLIP and YOLOX green; SCRFD amber (non-commercial weights).

**Round 2** resolved most cross-role questions directly:

- Systems can start WP-3 in sprint 2 against a draft WP-C, provided `DecoderPort.decode(request, deadline)` and the `ItemResult` status enum are frozen first.
- The Quality Engineer will test hangs and crashes through a `FaultyDecoder` adapter.
- Thumbnail scheduling lives in `services`, in front of a single decoder pool.
- Errors carry an exception class and error code only.
- Benchmark JSON has no file hashes, machine name or username, and gets an automated scrubber test.
- Starting caps are 120 MP per decode and a 30 s deadline.

## 3. Decisions (Architect)

| # | Decision | Rationale |
|---|---|---|
| D1 | **Order of owner activities:** (1) week 1 owner-PC sitting: headless POC run, HEIC sample corpus, hydration test, benchmark harness dry run. Nothing is shown. (2) Week 1–2: Windows Photos baseline on batch A. (3) Weeks 2–3: labelling sessions 1–3. (4) Week 6: M1 pilot on batch B. **Batches A and B are excluded from all labelling sessions.** Labelling session 1 moves from sprint 1 to sprint 2. | Avoids both AI-exposure bias and familiarity bias (PM, DS, UX) |
| D2 | **Data stays on the owner's PC.** Raw POC results, label files, content hashes and benchmark details stay local. Only aggregates leave: counts, rates with sample size and CI, timings, error-class histograms. The Security checklist, signed by the owner, gates every owner-PC activity. | Security; spec §16 |
| D3 | **WP-C content and freeze.** Sprint 1 delivers `ItemResult` (status enum `ok`, `unavailable`, `error`, `crashed`, `timeout`, `quarantined`; error class + code; decode and compute timings; no message text), `CacheKey` (every component in design 02 §4.1, canonical serialization), `DecoderPort.decode(request, deadline)` with a **required** deadline, and the UI–service contract draft. The `DecoderPort` signature and the `ItemResult` enum are frozen by mid-sprint; the rest freezes at merge. Later changes go in their own PR. | Unblocks WP-3 and QE in parallel (TL, Systems, QE) |
| D4 | **Decoder failure policy** is an implementation of ADR-0003, documented in the WP-3 low-level design: deadline (default 30 s), kill within a grace period, respawn, two-strikes quarantine, 120 MP pixel cap, one worker reserved for interactive requests, thumbnail scheduler in `services`. No new ADR. | Architectural intent unchanged |
| D5 | **No test seams in `src/`.** Faults are injected through ports (`FaultyDecoder`); kill-mid-commit uses a real process termination from the test harness. The POC keeps its marker; it is throwaway. | QE, Systems, Security |
| D6 | **New architectural invariants:** (8) the UI receives encoded bytes, never cache or source paths; (9) no UI action may trigger hydration, including any "open in Photos"; (10) error records, logs, diagnostics and benchmark output carry exception class and error code only, never message text, paths, usernames or file hashes. | UX, Security; added to design 01 §8 |
| D7 | **Export manifests carry no source details by default.** Files in the export folder list output names and opaque IDs only. Capture times and source hashes stay in the app database. | Security: the export folder is the one handed to print labs |
| D8 | **Python 3.12** is the CI reference. CI runs a Windows + Linux matrix. | QE, Architect |
| D9 | **Benchmark timings come only from the Systems harness**, so decode and inference are measured on the same hardware, cache state and versions. | Systems |
| D10 | **SCRFD is benchmark-only** (amber) unless nothing else is close and §22.7 confirms family-only use. YuNet, SigLIP and YOLOX are provisionally green, pending written verdicts. | Security, DS |
| D11 | **SigLIP zero-shot tags are internal signals only.** Their text prompts are versioned configuration owned by the Data Scientist. Any user-visible tags, search or captions are a change request. | PM, DS |
| D12 | **Labelling tool** is deliberately plain, lives in `tools/labeling/` (not `src/`), uses a different keymap from the review grid, and runs offline with the network guard. It may reuse the UX thumbnail-loading code. | UX: avoid practice effects |
| D13 | **Hydration test:** the Quality Engineer owns and runs it and keeps the OneDrive run log. Systems and Security attend the same sitting. Only instrumented runs count as §18.3 evidence. | TL, PM |
| D14 | **Ways of working:** one-week sprints; Friday written status from the Tech Lead; `needs:owner` label for owner-time issues; at most two open PRs per role; QE pre-reviews tests (time-boxed to one working day, written checklist); Systems reviews QE-authored test PRs; Architect gates Tech-Lead-authored PRs. | TL, QE |
